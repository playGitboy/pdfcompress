# PDF 批量压缩工具 (pdfcompress)

[English](README.en.md) | **简体中文**

一个基于 Go + Ghostscript 的**离线 PDF 批量压缩命令行工具**。单文件二进制、零依赖安装，支持  
**多文件与整个目录拖放**，可在**完全离线**的内网与办公终端上运行。

底层调用 Ghostscript 的 `pdfwrite` 设备重写 PDF 流，通过**图片降采样**与**字体内嵌子集化**  
两条路径大幅压缩体积，因而对**图片型（扫描件）**&#x548C;**文字型（电子公文）**&#x4E24;类 PDF 都有显著效果。

---

## 主要功能

- **批量处理**：一次可传入多个文件或整个目录；`-dir` + `-r` 递归处理子目录。
- **拖放即用**：把若干 PDF 文件（或文件夹）拖到程序图标上即可开始压缩，无需敲命令。
- **四级压缩**：`screen` / `ebook` / `printer` / `prepress`，在体积与清晰度之间自由权衡。
- **扫描件智能识别**：自动探测「图片像素被当作页面尺寸」的异常 PDF（手机/扫描仪导出的常见问题），  
  修正页面几何基准后再降采样，让这类文件也能真正压下来（见下文「扫描件几何基准自动修正」）。
- **并发加速**：默认并发数 = CPU 核数，配合单进程批量复用，98 个文件 / 948 MB 实测约 3.5 分钟。
- **安全覆盖**：`-overwrite` 先写临时文件、成功后再原子替换；**压缩后若未变小则保留原文件**，  
  绝不放大、绝不损坏原件。
- **失败兜底**：整块校验 + 逐文件重做 + 自动降级，任一步产物缺失都会重处理，不会把半成品当成功。
- **离线自包含**：内置便携 Ghostscript（Linux 版），目标机无需预装任何软件、无需联网。
- **零第三方依赖**：压缩探测与几何解析全部为纯 Go 标准库实现，无外部库依赖。
- **中文友好**：Windows 下双击运行时，出错也会**暂停等待回车**，不会一闪而过看不到报错。

## 使用方式

### 方式一：拖放（推荐给日常办公用户）

**Windows**

1. 解压离线包，得到 `pdfcompress.exe` 与同级 `gs\` 目录（**两者必须放在一起**）。
2. 选中一个或多个 PDF 文件，或直接选中一个文件夹。
3. 把它们拖到 `pdfcompress.exe` 图标上，松开即可开始压缩。
4. 输出文件与源文件同目录，命名为 `原文件名_ebook.pdf`（`_ebook` 即当前压缩级别）。

**Linux（麒麟 / 统信等 ARM64、x86_64）**

1. 解压 `PDFCompress-linux-<架构>.tar.gz`（**务必用 tar 解压，不要用图形界面复制**，
   否则可执行权限会丢失）：
   ```bash
   tar -xzf PDFCompress-linux-arm64.tar.gz
   cd PDFCompress-linux-arm64
   ```
2. **启用图形界面拖放**（推荐，只需执行一次）：
   ```bash
   sh 安装拖放.sh
   ```
   脚本会自动修复权限、在桌面创建「PDF压缩」图标，并注册到应用菜单。
   之后选中 PDF 文件或文件夹，**拖到该图标上松手**即可，会自动弹出终端窗口显示进度。
   若图标显示「未信任」，右键选择「允许启动」。

3. 也可直接用命令行：
   ```bash
   ./pdfcompress 文件1.pdf 文件2.pdf   # 与拖放等价的简写形式
   ./pdfcompress -dir ./待处理 -r      # 递归批量
   ```

> **关于 `安装拖放.sh`**：Linux 桌面（GNOME/KDE/UKUI/DDE）把「文件拖到程序图标」
> 实现为 `程序 文件1 文件2 ...` 的调用，需要一个 `.desktop` 启动器声明该入口。
> 主程序本就支持无参数启动时把位置参数当作待处理文件/目录，因此脚本只需生成
> `.desktop` 与一个终端包装器，**无需改动程序逻辑**。脚本会自动探测 10 种常见终端
> 模拟器（ukui-terminal / deepin-terminal / gnome-terminal / konsole / xterm 等），
> 并在压缩结束后等待回车，避免窗口一闪而过。

### 方式二：命令行

```bash
# 压缩单个文件
pdfcompress -i 输入.pdf -o 输出.pdf

# 批量处理目录（默认在输入目录下创建 compressed/ 子目录）
pdfcompress -dir ./待处理

# 递归处理子目录，指定级别与并发数
pdfcompress -dir ./待处理 -r -level printer -j 8

# 自定义 DPI（如 100 PPI，适合需要比 ebook 更小体积的场景）
pdfcompress -i 输入.pdf -level 100

# 覆盖原文件（先写临时文件，成功后替换；未变小时保留原文件）
pdfcompress -dir ./待处理 -overwrite

# 指定 Ghostscript 路径（默认自动查找内置 gs）
pdfcompress -dir ./待处理 -gs "C:\gs\bin\gswin32c.exe"
```

### 命令行参数

| 参数           | 说明                                               | 默认值                 |
| ------------ | ------------------------------------------------ | ------------------- |
| `-i`         | 输入 PDF 文件路径（单文件模式）                               | —                   |
| `-o`         | 输出 PDF 路径（单文件模式，与 `-overwrite` 互斥）               | —                   |
| `-dir`       | 输入目录（批量模式）                                       | —                   |
| `-out`       | 输出目录（批量模式）                                       | 输入目录下 `compressed/` |
| `-r`         | 递归处理子目录                                          | `false`             |
| `-level`     | 压缩级别：`screen` / `ebook` / `printer` / `prepress`，或自定义 PPI 数值（如 `100`） | `ebook`             |
| `-j`         | 并发工作数                                            | CPU 核数（上限 16）       |
| `-gsThreads` | 每个 Ghostscript 进程的渲染线程数                          | `0`（按并发数自动）         |
| `-persist`   | 批量模式复用单个 Ghostscript 进程（显著提速）                    | `true`              |
| `-chunk`     | 单进程处理的文件数                                        | `0`（自动）             |
| `-overwrite` | 结果覆盖原文件（未变小时保留原文件）                               | `false`             |
| `-gs`        | 指定 Ghostscript 路径                                | 自动查找                |
| `-q`         | 静默模式                                             | `false`             |
| `-version`   | 显示版本信息                                           | —                   |

### 压缩级别怎么选

| 级别         | 图片降采样                 | 典型用途                     |
| ---------- | --------------------- | ------------------------ |
| `screen`   | 72 DPI                | 体积最小；**中文小字会发糊，不建议用于公文** |
| `ebook`    | 150 DPI               | **默认**。屏幕阅读，体积与清晰度的最佳平衡  |
| `printer`  | 300 DPI               | 需要打印时使用，体积约为 ebook 的 3 倍 |
| `prepress` | 300 DPI + 单色 1200 DPI | 印刷级，体积最大                 |
| `10~2400`  | 自定义数值               | 如 `-level 100` 可在 screen 与 ebook 之间取折中 |

**自定义 PPI 数值**：`-level` 支持直接传入 10–2400 的整数（如 `-level 100`）。  
数值越小体积越小，但文字清晰度随之下降；建议屏幕阅读不低于 72，常规阅读不低于 100。

**两类 PDF 的实际表现（实测）：**

- **文字型（电子公文，几乎不含图片）**：体积 99% 以上来自未子集化的内嵌 CJK 字体，  
  压缩主力是**字体子集化**。实测 15.43 MB → 约 220 KB（**-98.6%**），且  
  **四个级别输出几乎逐字节相同**——这是正常现象，不是程序异常。
- **图片型（扫描件）**：四个级别差异明显。**源图有效分辨率高于目标 DPI 时即降采样**，
  因此级别越高、保留细节越多、体积越大（所以 `printer` 的体积通常明显大于 `ebook`）。
  源图分辨率本就低于目标 DPI 时不会上采样，体积也不会因此变大。

## 扫描件几何基准自动修正

### 问题：为什么有些扫描件压不动？

手机拍照、扫描仪导出的 PDF，常常把**图片的像素数直接当作页面尺寸（pt）**。  
例如一张 2736×3648 像素的照片，被写成 2736×3648 pt 的页面（正常 A4 只有 595×842 pt）。

Ghostscript 会据此反推**有效 DPI = 72**（2736 px ÷ (2736 pt ÷ 72)），低于所有压缩级别的  
阈值，于是判定「无需降采样」——`screen` / `ebook` / `printer` 三档输出**几乎逐字节相同**，  
压缩率接近 0。这正是「明明是大文件却压不下去」的根本原因。

### 解法：智能判定，而非一刀切

程序内置一个**零依赖的明文几何探测器**（`pdfgeom.go`），扫描 PDF 中的 `/MediaBox`，  
按下列**三分支逻辑**决定是否修正：

| 判定 | 条件 | 行为 |
| --- | --- | --- |
| **标准纸张** | 命中 A4 / A3 / A5 / Letter / Legal 等标准规格 | **完全走原逻辑**，不做任何改动 |
| **像素当 pt** | 尺寸明显超限（长边 > 1300 pt）**且**含图像**且**异常页占多数 | 启用几何基准修正 |
| **无法判定** | 解析失败 / 页面对象在压缩流（ObjStm）中 / 自定义尺寸 | **保守不动**，走原逻辑 |

修正时注入 `-dFIXEDMEDIA -dPDFFitPage`，把页面重设为**比例最接近的标准纸张**，  
并用 `-r<级别DPI>` 重设分辨率基准，让 Ghostscript 能算出真实 DPI、正常降采样。  
**目标尺寸保留原始纵横比**（长边对齐纸张长边、短边按原比例换算），  
避免 4:3 照片被硬套 A4 造成约 6% 的拉伸变形。

### 实测效果

- 89 份 / 948 MB 真实语料：**83 份标准纸张（零改动）/ 4 份像素当 pt（修正）/ 2 份保守不动**。
- 4 份修正文件三档成功拉开（修正前几乎相同）：
  | 文件 | 源大小 | screen | **ebook（默认）** | printer |
  | --- | --- | --- | --- | --- |
  | test (1) | 18.39 MB | 188 KB | **753 KB** | 3.1 MB |
  | test (63) | 24.51 MB | 285 KB | **1425 KB** | 1425 KB |
  | test (64) | 23.33 MB | 108 KB | **337 KB** | 1091 KB |
  | test (104) | 4.75 MB | 31 KB | **113 KB** | 290 KB |
- **标准 A4 零影响**：同一份公文在修正前/后输出同为 271,669 字节，逐字节差异仅 75 字节  
  （全部是时间戳与文档 ID），交叉引用表逐字节相同。
- **比例偏差 ≤ 0.04%**（仅取整误差）。
- 视觉验证：`ebook` 档（约 1/24 体积）标题与正文全部清晰可读。

> 该特性对**纯文字 PDF 不做修正**（无图像则修正无收益，反而会因页面结构改写而略微增大体积）。

## 图片降采样阈值修正（让档位 DPI 成为真正的上限）

### 问题：为什么标准 A4 的扫描件也压不动？

页面尺寸正常（A4）但**图片分辨率偏高**的扫描件，在默认 `ebook`(150 DPI) 档往往压缩率接近 0。
原因有两个，且都与「档位 DPI 没有被真正执行」有关：

1. **`DownsampleThreshold` 默认为 1.5**，含义是「源分辨率 > 目标 × 1.5 时才降采样」。
   200 DPI 的扫描件在 150 DPI 档下：`150 × 1.5 = 225 > 200` → **一个像素都不降**。
2. **JPEG 透传**（`-dPassThroughJPEGImages=true`）会把没被降采样的原图**原样搬进输出**，
   于是输出比原文件还大几十~几百字节，被安全网判为「未变小」而保留原文件 ——
   用户看到的就是**压缩率 0%**。

### 解法

在基础参数中把降采样阈值降为 **1.0**（只要高于目标分辨率就降采样），
并**关闭 JPEG 透传**（强制按目标分辨率重新编码）：

```
-dColorImageDownsampleThreshold=1.0
-dGrayImageDownsampleThreshold=1.0
-dMonoImageDownsampleThreshold=1.0
-dPassThroughJPEGImages=false
```

这样「`screen`=72 / `ebook`=150 / `printer`=300 DPI」的语义才成立，各档位稳定拉开差距。

### 实测效果

- 8 份「未有效压缩」样本（200 DPI 扫描件，A4）：`ebook` 档由 **8/8 全部 0%**
  变为 **7/8 有效压缩，合计 42.2%**；其中 `test(2)` 2.68 MB→0.64 MB、`test(8)` 651 KB→170 KB。
- 89 份 / 948 MB 全量语料：**947.40 MB → 169.70 MB（-82.1%）**，
  对比修正前的 179.75 MB（-81.0%），**12 份文件净减 10.0 MB，其余 76 份字节级零变化**
  （差异仅 ≤118 字节的时间戳），**零体积回归**；耗时 4m04s → 4m31s（+11%）。
- 画质（渲染到 150 DPI 后逐像素比对）：`test(2)` MAE 3.5/255、`test(8)` MAE 3.0/255
  （肉眼无感）；**密集小字表格类扫描件**（如 `test(1)`）MAE 约 12/255，
  属 200→150 DPI 降采样的固有代价 —— 这类文件如需更高保真请选 `printer` 档。

## 支持的系统（均可离线使用）

| 平台      | 架构              | 离线包                               | 运行要求                                              |
| ------- | --------------- | --------------------------------- | ------------------------------------------------- |
| Windows | x86（32 位）       | `pdfcompress-windows-x86.zip`     | **Windows 7 / 8 / 10 / 11**，32 位与 64 位系统均可（WoW64） |
| Linux   | ARM64 (aarch64) | `PDFCompress-linux-arm64.tar.gz`  | 麒麟 V10 / 统信 UOS 等，**内置便携 Ghostscript，免安装免联网**     |
| Linux   | x86_64 (amd64)  | `PDFCompress-linux-x86_64.tar.gz` | 同上                                                |

- **完全离线**：所有离线包均已包含运行所需的全部文件，目标机无需安装 Ghostscript、  
  无需联网、无需 Node/Python 等任何运行时。
- **Windows 版为何只有 32 位**：为兼容 Windows 7，编译使用 Go 1.19；单一 x86 版本可  
  通过 WoW64 同时运行在 32 / 64 位系统上，部署最简单。
- **Linux 版内置 Ghostscript**：采用 musl 静态链接版本，与发行版 glibc 解耦，  
  不受系统 Ghostscript 版本影响；主程序会自动优先使用同目录下的 `gs/`。

## 从源码构建

需要 **Go 1.19.x**（更高的 Go 版本将无法在 Windows 7 上运行）。

```bash
# Windows x86（兼容 Win7 的 32 位版本）
CGO_ENABLED=0 GOOS=windows GOARCH=386 \
  go build -trimpath -buildvcs=false -ldflags "-s -w" -o pdfcompress.exe

# Linux ARM64（麒麟 / 统信）
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 \
  go build -trimpath -buildvcs=false -ldflags "-s -w" -o pdfcompress

# Linux x86_64
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
  go build -trimpath -buildvcs=false -ldflags "-s -w" -o pdfcompress
```

> 注意：必须 **整包编译**（在项目根目录执行 `go build .`），  
> 否则 `console_windows.go` 等平台文件不参与构建，双击检测会失效。

如需进一步缩小体积，可用 UPX 加壳：

```bash
upx -9 pdfcompress.exe      # 2.09 MB → 1.04 MB（含图标与版本信息）
upx -9 pdfcompress          # 1.77 MB → 0.66 MB (arm64)
```

> UPX 加壳可能被部分国内杀毒软件误报，正式部署前请先做白名单验证。  
> 加壳是无损可逆的：`upx -d` 解包后与原文件逐字节一致。

### 为 Windows 版添加图标与版本信息

Windows 版的图标和「属性 → 详细信息」由包目录下的 `winres.syso` 提供：
Go 在构建 windows 目标时会自动链接同级目录中的 `*.syso`（COFF 目标文件）。
这两个脚本**纯 Python 实现，不依赖 windres / mingw / go-winres**，可在离线环境使用：

```bash
# 1) PNG → 多尺寸 ICO（生成 app.ico，含 16/24/32/48/64/128/256 七个尺寸）
python png2ico.py pdf.png app.ico

# 2) ICO + 版本信息 → winres.syso
python make_syso.py winres.syso app.ico 2.1.0

# 3) 正常整包编译，资源会被自动嵌入
CGO_ENABLED=0 GOOS=windows GOARCH=386 \
  go build -trimpath -buildvcs=false -ldflags "-s -w" -o pdfcompress.exe
```

要改公司名、产品名、描述等，直接编辑 `make_syso.py` 中 `main()` 里的 `info` 字典即可。

> 该脚本生成的是 32 位（i386）COFF，仅用于 `GOARCH=386` 的 Windows 构建。
> Linux 版不需要、也不应放置 `winres.syso`。
